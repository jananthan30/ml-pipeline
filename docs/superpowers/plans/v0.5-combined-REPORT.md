## Base choice

PR #11 was the base, as asked. Reading both lines confirmed it is the cheaper direction:

- PR #11 moved the library to `skills/ml-pipeline/lib/` and rewrote it around streaming (1,726 lines:
  `scan`, `load_sample`, sketches, `split_to_files`, batched `final_test`). Moving that onto the
  data-work line would mean re-deriving every streaming path.
- PR #11's approval model (UserPromptSubmit hook, `.approvals.json`, tamper protection, step order)
  touches every gate check. The data-work line's checks are self-contained (`hooks/gate_records.py`,
  plus separate helper functions), so they could be added to PR #11 as they are.

## Decisions

Where both lines solved the same thing, the stricter behaviour was kept.

1. **Ledger parsing: strict shapes (data-work line).** PR #11 accepted any line mentioning a gate and
   "approved" unless a negation word appeared. With the user's chat approval in place, PR #11's hook
   allowed `- Gate B: to be approved by the user`, `- Gate B needs an approved model rationale first`,
   and `- Gate B: never approved` (probe against PR #11's hook with real approvals: 9 of 23 wrong).
   Now only `- Gate X: approved ...` and `- Override: <what> - ...` count, the last line per gate
   decides, and only in the newest run.
2. **Approvals: both rules.** A gate counts only with the strict ledger line AND the user's chat approval
   given in the same run. The approval rule was not weakened.
3. **Overrides need the records** (data-work amendment 4) plus the user's chat override (PR #11).
4. **No target statistics before the split (data-work decision 6) over PR #11's ranked EDA.** The
   profile no longer publishes `feature_signal`; it is still computed internally for the leak scan.
   Step-2 figures leave the target out: removed `02_feature_vs_target*`, `02_categorical_vs_target*`,
   target drift in `02_temporal_coverage`, the target row in `02_correlations`; `02_feature_overview`
   now plots missingness against distinctness; the summary drops "Strongest target signal".
   Feature-target strength comes from `guard.train_associations` on the training split.
5. **Every column drawn (data-work) over capped numeric pages (PR #11).** `eda_figures` calls
   `variable_figures`, which puts every column of every kind on 12-column pages with `pages.json`;
   PR #11's `02_distributions_pN` pages and their `max_pages` cap are removed.
6. **"No sampling" vs big data.** The data-work spec says every statistic uses every row; PR #11 samples
   for distribution statistics. Kept: every count and moment is exact over every row, streamed (missing,
   non-null, distinct counts, min/max, mean/std/skew/kurtosis, zeros, negatives, outliers against the
   sample's quartile fences, level counts up to 10,000 levels, target class counts, text lengths, date
   range). Only percentiles and figures use the uniform sample when the data exceeds `SAMPLE_ROWS`, and
   the profile says so (`shape.sampled`). This keeps the full-data proof and the label-audit cross-check
   exact while profiling files larger than memory.
7. **Full-data proof for files.** A path given to `guard.profile` is hashed and recorded in
   `source.json`, and the profile is tied to it; a DataFrame must match a source from `guard.load` /
   `guard.derive`. `profile(..., source=)` from the data-work line is renamed `source_name=` because
   PR #11's first argument is already `source`.
8. **Records read the profile.** `data_dictionary`, `categorical_plan` take kinds and statistics from
   the profile (one source of truth for the hook's cross-checks); `missingness` and `label_audit` stream
   the data for exact counts; label conflicts are found by sorting row hashes (16 bytes per row).
9. **Final test: stricter of both.** A touch is allowed only when total touches stay within 1 + the
   user-approved strict `final test` override lines over the whole ledger (PR #11's invariant), and at
   least one such override is in the newest run (data-work rule). Touches are counted from the state
   file and the ledger's final-test lines over all runs, so a `## Run:` heading never resets single use.
   A used test set can't be re-split (`split` and `split_to_files`).
10. **Two run logs kept.** PR #11's `runs.jsonl` (`log_run`, metrics for steps 9-11) and the data-work
    `training_runs.jsonl` (`guard.fit` receipts proving a full-data run) answer different questions;
    Gate C requires both.
11. **`.txt` files are scanned at write time** (data-work behaviour, probe expects DENY). On PR #11,
    only run time caught it: its own test (`ExecutedScripts.test_code_hidden_in_a_txt_file_is_scanned_when_run`)
    asserted that writing fit code to `notes.txt` is allowed and `python3 notes.txt` is denied, and the
    probe's ".txt" row read ALLOW against PR #11's hook. Now both catch it: writing it is denied, running
    it is denied before Gate B and allowed after
    (`tests/test_guard_training.py::ExecutedScripts::test_code_hidden_in_a_txt_file_is_scanned_when_written_and_when_run`).
12. **Self-disable covers three switches:** `ML_PIPELINE_ENFORCE`, `ML_PIPELINE_FILE`, and
    `ML_PIPELINE_REQUIRE_USER_APPROVAL` (the last would weaken the approval rule). The check runs before
    the config-file skip, so `.claude/settings.json` is covered.
13. **`jupyter nbconvert` without `--execute`** is not treated as a run (data-work test); PR #11 read
    the notebook for any `jupyter` command.
14. **CI:** stdlib job adds the data-work hook tests and the probe; the full job runs everything
    including the end-to-end and canary tests; `scikit-learn` added to `tests/requirements-dev.txt`;
    `actions/setup-python` pinned to a commit SHA (the only scanner findings, present in PR #11 too).
15. **Probe ledger cases carry real chat approval** through `hooks/record_approval.py` (subprocess),
    for all 8 ledger cases, not only the two that changed outcome — so each one tests ledger parsing.
    The probe keeps 23 cases and now runs the hooks with the same interpreter as the probe.
16. **A column the sample misses entirely** (nearly all empty, on data larger than `SAMPLE_ROWS`) still
    gets every profile key: the exact counts and moments from the full pass, and `null` for the
    sample-only percentiles. Before this fix such a column blocked Gate A for good ("lacks describe/info
    statistics", which re-profiling could not cure). Test: `NearlyEmptyColumnsOnBigData` in
    `tests/test_guard_data_work.py`.
17. **Eval `wide-data`:** the grader no longer asks for the strongest signals before the split (that
    contradicts decision 4); it asks for the leak, the coverage, and that strength is measured on train.

  figure → steps 9–12 → Gate C → step 13 → batched `final_test` from the test file → Gate D. All allowed.

## Unfinished, untested, or known limits

- **CI has not run on this branch.** `tests.yml` and `hol-plugin-scanner.yml` trigger only on pushes to
  main/master and on pull requests, and no PR was opened (as instructed). All evidence here is from
  local runs.
- The data-work spec mentions Python 3.9 for the hooks; neither CI nor this merge tests 3.9 (3.10, 3.11,
  3.13 pass).
- **The CI scanner action** pins `ai-plugin-scanner-action` v1.2.683; locally I ran the PyPI
  `plugin-scanner` 3.58.0 from the same publisher. Results could differ slightly in CI.
- **Evals were not executed** (they need live agent runs). `understand-first` gained the data-work
  graders; `wide-data`'s LLM grader was rewritten (decision 17) and is unverified against a run.
- **Percentiles and figures are sampled** above `SAMPLE_ROWS` (decision 6). Level counts are exact up to
  10,000 levels per column, then the top levels come from the sample (`levels_exact: false`).
  `label_audit` holds 16 bytes per labelled row in memory.
- **Out-of-core cleaning:** `log_cleaning` compares two in-memory frames; for data that does not fit,
  record the rule on the affected rows or use `- Cleaning: none needed - reason: ...`.
- The hooks are pattern checks, not a sandbox (as the README says): code written to evade them can run.
- The ported design and plan documents describe the data-work line as it was (library at `lib/`); this
  report and the CHANGELOG describe the combined result.
